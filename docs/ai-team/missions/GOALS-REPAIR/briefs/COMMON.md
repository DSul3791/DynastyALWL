# GOALS-REPAIR — common rules for every work-package thread

Read this before your package brief. The lead thread is "Repair progression and build player guide". The tracker files are [../STATE.md](../STATE.md) and [../REPAIR_DECISIONS.md](../REPAIR_DECISIONS.md).

1. **Base.** Start from the latest `origin/dev` of DSul3791/DynastyALWL. Read CLAUDE.md, docs/START_HERE.md, docs/ai-team/ (CONSTITUTION, DECISION_AUTHORITY, TEST_GATES) and docs/PONYTAIL_RULES.md from `dev`. PRs target `dev`. Never touch `main`. Decision 61 applies: replaced code is deleted, not flagged off.
2. **Authority.** Use the approved design documents named in your brief. Use code and data as implementation evidence. Historical audit text, old station names and old recipes are not rules.
3. **Open values.** Ruling R-1 in REPAIR_DECISIONS.md lets a named feature use a provisional value. Each one gets the tag `PROVISIONAL (GOALS-REPAIR A-n)` in data, as a `"_provisional"` note field or adjacent comment, whichever the file's conventions allow. Each one also needs an entry for the lead to add to REPAIR_DECISIONS.md §4, with these fields: question, value, precedent (current documents first, then the closest current in-game analogue, and an obsolete source only when nothing current exists, saying so), files and commits, and how to change it. Never call a provisional value approved. R-1 does not cover renames, removals or retirements of existing items, reward amounts or payouts, Map Scroll mechanics, `main`, or destructive or security-sensitive steps. Send those to the lead.
4. **Shared files.** Use only the shared-file sections your brief assigns you. The lead holds the ownership table in STATE.md. Ask the lead before editing anything else in `src/stream/server_items.gd`, shared `data/items/*.json`, `src/stream/terrain_net.gd` PROTOCOL_VERSION/PROTOCOL.md, or `src/client/terrain_client.gd`. Rebase on `dev` before each merge.
5. **Tests.** Godot never runs in the cloud. Write the tests, then record `python3 tools/tests_for_diff.py origin/dev HEAD` (read its `why`). Ask the coordinator for a lane B (David4) run on the exact reviewed SHA. Record test evidence as STATIC_READ / AUTOMATED_TEST / HEADLESS_GODOT / PLAYED_F6 / MULTIPLAYER_RESTART. A test that admin-spawns materials or calls the server directly proves only the isolated mechanic. It does not prove the player route.
6. **Review.** Every PR gets an independent gate-reviewer pass on its exact head before merge. Fix substantive findings and stop re-reviewing once none remain. Merge to `dev` through GitHub from the cloud side.
7. **Reporting.** When each PR merges, message the lead thread with the PR, the dev merge SHA, the test evidence, the provisional values (with their A-n entries) and any outside defects. Keep Dave's updates short. Detail goes in GitHub.
8. **Goals.** Do not change goal reward amounts. Use stable goal IDs. When a station or item that a goal names changes meaning, tell the lead. The lead owns goal content (R7).
