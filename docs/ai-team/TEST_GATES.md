# Validation gates and trusted testing environment
**Status: IN FORCE. Consolidated 15 Nov 2026 under Dave's approved four-rulebook structure.** Implement mechanical enforcement, not prompt-only promises.

## Review and evidence by risk
Author self-review is followed by non-author review before integration. Review depth follows the actual diff and consequences: a typo/link correction needs a light documentation check; changes to authority, creative policy or safety boundaries need source/impact review and applicable Dave authorization. Changed code/data needs the relevant checks below. A documentation-only change does not require a new Godot run or create new gameplay-playability evidence; static/package/link checks and non-author review apply. Changes to executable tools still require checks appropriate to their behavior.

Record the exact reviewed head and relevant base. Subsequent edits require review of the additional diff and its change plan. A clean merge of `dev` into a reviewed branch follows **Carry-over after a merge of dev** below. A green result on another SHA is evidence with a scope, not a blanket PASS. Do not claim an independent review happened when only author self-review ran.

Required critical failures hold integration. A known noncritical baseline defect or unavailable optional check needs a bounded explanation and reviewer disposition; do not silently ignore it or demand unrelated repairs. Deferred broader checks retain an owner and a specific integration/release checkpoint, and remain visible until discharged.

## dev playtest gate (runtime changes and nightly playable candidates)
1. Agent commits are recorded; dev merge result is an immutable **exact SHA**.
2. The change plan (`Test plans for dev` below) passes on the proper machine **on the exact reviewed head, or on the trial merge of a reviewed batch, before every merge into `dev`**. No overnight, unattended or time-pressure exception: a change whose change plan has not passed waits; it is not merged and labeled 'untested'. A selector `docs` class needs no Godot run. The full suite is not run per change (Dave, 19 Nov 2026, thread "Enforce tests before every merge": "make sure we are doing tests again also make sure they are dynamically choosing tests accordingly to streamline the process while not wasting tokens but still being effective").
3. Dedicated local Godot 4.7.2 voxel-tools build loads correct scene; PC-based startup/world load smoke test passes without stealing resources from Dave's active playtest.
4. Dev reviewer checks contract compliance, no unapproved data schema migration, and no known critical regression. Changed visual/audio content is explicitly marked 'not visually checked' unless evidence exists.
5. Every skipped/blocked gate, newly introduced serious defect, and known issue appears in short dev release notes and machine-readable test evidence. If critical smoke fails, do NOT announce dev playable. If smoke test could not run because Dave is playing or local access is unavailable, say `DEV COMMITTED — PLAYABILITY UNVERIFIED` and offer the last known green SHA. Never label NOT RUN as PASS.

## Test plans for dev
Two plans, both from `tools/tests_for_diff.py` (rules in `tools/test_lanes.json`; always read the plan's `why`):

**1. Change plan, every PR before it merges into `dev`:** `python3 tools/tests_for_diff.py origin/dev <head>`. It holds: the tests the PR adds or edits; every test that loads a changed file directly (the test itself or a `src/worldgen/tools` helper it uses); for a hub (a file 100 or more tests load directly: today `terrain_net.gd`, `server_items.gd`, `item_table.gd`) the hub's core list plus every test that names a function, constant or signal the diff changed there (an `@rpc` line counts as its function, a private helper as its public callers; a name more than 40 tests use, such as `setup`, selects a fixed spread of 40 of them; an added, deleted or renamed hub selects every fast test); the always set (11 tests); the item group and its `validate_items` check for item data; the path rules (looks with the warnings and look-name checks, sounds, water, building wear, footprints); baked-data tests for a bake. An unknown path, a `project.godot` edit or a test file the scan cannot read still selects every fast test. The cloud `merge_check.py` (including `export_check.py`, now a failure for server-only code in the client: run `python3 tools/export_check.py --write`, also after a merge conflict on its generated exclude line) runs on every PR. Run the plan as printed: do not add `--all`, `--full` or extra smokes for a routine change, and do not cut it.

**2. Wide plan, the dev sweep, once per batch of merges:** `python3 tools/tests_for_diff.py <last green sweep SHA> <dev head> --wide`: every test that reaches a changed file through any chain of loads, on the exact `dev` head. It replaces running that wide set for each PR (it was 200 to 450 tests per PR on 21 Nov). It runs when a lane is free and `dev` has code merges since the last green sweep, at least once a day `dev` took code merges, and before `dev` is frozen for a `main` gate (a red found by the gate costs a whole gate rerun). The coordinator records the last green sweep SHA in its state record. A sweep does not block merges. A red sweep: rerun the failing tests alone once (the lane's retry rule); still red, find the culprit by running only those tests on the first-parent merge commits in the range, halving the range each time. The culprit's owner fixes forward in a new PR under the normal rules; if the red blocks Dave's play or is not fixed within a day, the coordinator reverts that merge by PR. An open sweep red is a known issue in every dev release note and blocks freezing `dev` for `main`.

**Batches:** several PRs, each reviewed on its exact head, may share one lane run: trial-merge them in order onto current `dev` and run the change plan of the result (`tests_for_diff.py origin/dev <trial merge>`). Green: merge them in that order with no further run (each PR's own diff must still be the reviewed one, `--same-change`). Red: run only the failing tests on trial merges of half the batch, then of single PRs, to find the culprit; drop it and merge the rest once those tests pass without it. Keep a batch to about five PRs so a red is cheap to split.

**Carry-over after a merge of dev:** when a reviewed branch takes a merge of `dev` and `python3 tools/tests_for_diff.py --same-change <reviewed head> <new head>` exits 0 (its own change is the same patch), the review and the change-plan result carry over to the new head: no re-review, no rerun. A clean textual merge can still break meaning (dev renamed something the branch calls); that interaction is the sweep's job. Otherwise (a conflict resolution or a new edit), review the interdiff only and run the change plan of the new head.

Real protocol, serialization or save changes: the plan may grow, never shrink, for the named risk (both sides of the protocol, authorization, saves). Approval of the change itself is not decided here: breaking protocol or save changes are Class C (`CONSTITUTION.md`). Never bypass required CI, weaken security/data-integrity or multiplayer checks, edit `test_lanes.json` just to avoid a run, or relax the `main` promotion gate. Gate tooling edits run the lane check and selftest (`tools/selftest_gate_tools.sh`). Distinguish machine test runtime from Claude token cost; retain full test artifacts but send concise summaries.

## Evidence format
Task ID, base SHA, head SHA, final merged SHA (if any), runner identity, machine, tool/Godot version, test plan, test counts including skips, output location, screenshots/visual review if applicable, reviewer, decision on safe promotion. For a dev change also: the plan type (change, batch or sweep), its `why`, the PRs in a batch, and for a carry-over the `--same-change` result. A claim without output/commit reference is NOT a passed gate. Report implementation, review, automated verification, dev integration and player validation as distinct states. Visuals, sound and feel remain unverified without appropriate observation; static review or a headless smoke cannot certify them.
