# Validation gates and trusted testing environment
**Status: IN FORCE. Consolidated 15 Nov 2026 under Dave's approved four-rulebook structure.** The `main` promotion gate is in `MAIN_GATE.md`.

## Review and evidence by risk
Author self-review is followed by non-author review before integration. Review depth follows the actual diff and consequences: a typo/link correction needs a light documentation check; changes to authority, creative policy or safety boundaries need source/impact review and applicable Dave authorization. Changed code/data needs the relevant checks below. A documentation-only change does not require a new Godot run or create new gameplay-playability evidence; static/package/link checks and non-author review apply. Changes to executable tools still require checks appropriate to their behavior.

Record the exact reviewed head and relevant base. Edits after a review and merges of `dev` follow **Carry-over after a merge of dev** below. A green result on another SHA is evidence with a scope, not a blanket PASS. Do not claim an independent review happened when only author self-review ran.

Required critical failures hold integration. A known noncritical baseline defect or unavailable optional check needs a bounded explanation and reviewer disposition; do not silently ignore it or demand unrelated repairs. Deferred broader checks retain an owner and a specific integration/release checkpoint, and remain visible until discharged.

## dev playtest gate
Before every merge into `dev`, on the exact head (or the trial merge of a reviewed batch):
1. Independent non-author review of that head (see above).
2. The change plan (`Test plans for dev` below) green on a lane. No overnight, unattended or time-pressure exception: a PR whose plan has not passed waits; it is not merged and labeled 'untested'. A selector `docs` class needs no Godot run. The full suite is not run per change (Dave, 19 Nov 2026, thread "Enforce tests before every merge": "make sure we are doing tests again also make sure they are dynamically choosing tests accordingly to streamline the process while not wasting tokens but still being effective").
3. Warnings no higher than the baseline, look names drawable, and `MERGE_CHECK_BASE=origin/dev python3 tools/merge_check.py` passing (the plan's checks and the cloud CI).
4. A change to looks or movement: pictures from the in-game tools, seen by the coordinator before the merge. Visuals not looked at are marked 'not visually checked'.
5. One PR merges at a time; if `dev` moved, merge `dev` in and use the carry-over rule. The gate record is a PR comment. Never label NOT RUN as PASS.

## Test plans for dev
Two plans, both from `tools/tests_for_diff.py` (rules in `tools/test_lanes.json`; always read the plan's `why`):

**1. Change plan, every PR before it merges into `dev`:** `python3 tools/tests_for_diff.py origin/dev <head>`. Run the plan as printed, read its `why`, never add `--all`, `--full` or extra smokes and never cut it. How it picks tests is in the tool's own help (`tools/tests_for_diff.py` header) and `tools/test_lanes.json`. `tools/run_tests.sh --plan` runs the plan's listed checks too; a listed check it cannot run fails the run with a "CHECKS NOT RUN" line. The cloud `merge_check.py` runs on every PR (it includes `export_check.py`: run `python3 tools/export_check.py --write` after a conflict on its generated exclude line).

**Watched checks:** a new check starts warn-only. Each problem line it finds is flagged every time a change touches its file; the 3rd such change is blocked until that problem is fixed or removed, and then its count is gone. Keys, tokens, passwords and private files block on first sight (`tools/warn_watch.py`; a new watched check is one more name in `tools/hooks/agent_warn.py` `line_problems()`; `docs/RULINGS.md` R-TEAM-WARN-TO-BLOCK, R-TEAM-NO-SECRETS). Never loosen or reset a watched check to get green.

**2. Wide plan, the dev sweep, once per batch of merges:** `python3 tools/tests_for_diff.py <last green sweep SHA> <dev head> --wide`: every test that reaches a changed file through any chain of loads, on the exact `dev` head. It replaces running that wide set for each PR (it was 200 to 450 tests per PR on 21 Nov). It runs when a lane is free and `dev` has code merges since the last green sweep, at least once a day `dev` took code merges, and before `dev` is frozen for a `main` gate (a red found by the gate costs a whole gate rerun). The coordinator records the last green sweep SHA in its state record. A sweep does not block merges. A red sweep: rerun the failing tests alone once (the lane's retry rule); still red, find the culprit by running only those tests on the first-parent merge commits in the range, halving the range each time. The culprit's owner fixes forward in a new PR under the normal rules; if the red blocks Dave's play or is not fixed within a day, the coordinator reverts that merge by PR. An open sweep red stays on the coordinator's known-issue list and blocks freezing `dev` for `main`.

**Batches:** several PRs, each reviewed on its exact head, may share one lane run: trial-merge them in order onto current `dev` and run the change plan of the result (`tests_for_diff.py origin/dev <trial merge>`). Green: merge them in that order with no further run (each PR's own diff must still be the reviewed one, `--same-change`). Red: run only the failing tests on trial merges of half the batch, then of single PRs, to find the culprit; drop it and merge the rest once those tests pass without it. Keep a batch to about five PRs so a red is cheap to split.

**Carry-over after a merge of dev:** when a reviewed branch takes a merge of `dev` and `python3 tools/tests_for_diff.py --same-change <reviewed head> <new head>` exits 0 (its own change is the same patch), the review and the change-plan result carry over to the new head: no re-review, no rerun. A clean textual merge can still break meaning (dev renamed something the branch calls); that interaction is the sweep's job. A push after a review PASS that only fixes that review's own findings needs no new review round (the author checks each fix against its finding); it runs the change plan of the new head. Otherwise (a conflict resolution or any other edit), review the interdiff only and run the change plan of the new head.

Real protocol, serialization or save changes: the plan may grow, never shrink, for the named risk (both sides of the protocol, authorization, saves). Approval of the change itself is not decided here: breaking protocol or save changes are Class C (`CONSTITUTION.md`). Never bypass required CI, weaken security/data-integrity or multiplayer checks, edit `test_lanes.json` just to avoid a run, or relax the `main` promotion gate. Gate tooling edits run the lane check and selftest (`tools/selftest_gate_tools.sh`). Distinguish machine test runtime from Claude token cost; retain full test artifacts but send concise summaries.

## Evidence format
Task ID, base SHA, head SHA, final merged SHA (if any), runner identity, machine, tool/Godot version, test plan, test counts including skips, output location, screenshots/visual review if applicable, reviewer, decision on safe promotion. For a dev change also: the plan type (change, batch or sweep), its `why`, the PRs in a batch, and for a carry-over the `--same-change` result. A claim without output/commit reference is NOT a passed gate. Report implementation, review, automated verification, dev integration and player validation as distinct states. Visuals, sound and feel remain unverified without appropriate observation; static review or a headless smoke cannot certify them.
