# Documentation authority, provenance and synchronization
**Status: IN FORCE; reconciled 15 Nov 2026 on Dave's instruction.**

## Resolve authority before editing
Start from current `origin/dev`: `CLAUDE.md` -> `docs/START_HERE.md` -> `docs/DOC_MAP.md` and the task's current mission state/decision record. Use accessible private handoffs for their scoped evidence. The 11 Nov Library index, `docs/PROJECT_START_HERE.md`, and installation package are historical navigation, not current authority. Missing old mounts do not block work when current repo sources suffice; identify a specific missing decision if they do not.

Authority is per topic and decision, not file age or a CURRENT label. Approved design describes intended behavior; code/data describes implemented behavior; observed tests describe verified behavior. Keep all three separate. Later scoped delegation is resolved under `DECISION_AUTHORITY.md`. Never silently let implementation override creative intent.

## Record substantive decisions
For meaningful decisions retain ID/topic, source or exact human quotation when available, date/actor, scope, status, selected choice, reason, superseded decisions and affected docs/code/checks. Separate AI interpretation. Statuses: DIRECTOR-APPROVED / DELEGATED / PROVISIONAL / PROPOSED / REJECTED / SUPERSEDED / NEEDS-REVIEW. Mark missing originals SOURCE UNVERIFIED; never fabricate quotes. Provisional values need a practical retuning path. Use the existing mission log; do not create a new record for every routine action.

## One master and proportionate updates
1. Read the topic's current spec, applicable decisions, rejected ideas and relevant contracts.
2. Update the authoritative instruction in place; remove contradictory prescriptions from active prose. Keep essential history in dated evidence, archives or Git history. Retired documents follow `RULES.md` archival policy; replacing a paragraph does not require preserving it as another active override note.
3. Check affected entry points, templates, agent instructions and indexes. Change related routing, not unrelated gameplay designs or balances.
4. Obtain non-author review proportionate to the change under `TEST_GATES.md`: links/status/typos need a light check; authority or creative-policy changes need source and consequence review plus Dave's authorization.
5. Record commit and validation evidence. Name the authoritative location; update an explicitly maintained secondary copy with receipt/hash, or mark SYNC PENDING. A repo change is not proof that private Library copies, account skills or live project settings changed.

Repo owns version-controlled operating, design, interface and code documents. Private handoffs/artifacts retain their established owner unless explicitly migrated. Do not edit two competing masters or copy the whole rulebook into launch instructions. Preserve rejected proposals as history.

## Suspected restrictions
Trace strong words (must/never/only/forbidden) to an approved human decision, verified technical necessity or security requirement. AI recommendations and unexplained paraphrases are not unconditional bans. Investigate without suppressing a plausible solution; disclose consequential conflicts with the exact path and source. A specific credible safety/data-loss problem still holds the affected action. Questions for Dave concern genuine decisions and human judgment, not technical choices agents can resolve.
