## Step 1 cost, step 2 hold rivers (31 Oct, evening): done, rated 3.5 of 5
- **Why the window never slept:** not a lake ringing. Rest snap is in (a block at rest zeroes its discharges: lakes and still pools sleep, tested by the dam-break and bowl checks), but the starter window is mostly river and falls, with discharges of 0.1 to 8 m2/s: that water really moves. `probe_water_cost.gd` shows it.
- **Cost, measured** (1 km window, 128 x 128 cells, 2,900 wet cells = 18 percent): was 224 ms of compute per simulated second (4 substeps a second, 3.4 us per cell, the deep sea set the time step); now **92 ms per simulated second** (the held sea no longer sets the time step, blocks with no water channel are never stepped). That is about 32 us per wet cell per simulated second. The hub thread runs at a 50 percent duty cap, so real time needs 9 percent of one core. Main-thread cost is only the old `set_sim` hand-over; `publish_levels` is 11 ms on the water thread every 15 s. The target "well under 4 ms per server tick" holds for the main thread; the thread is the cost. One window only: a whole tile is 225 windows, so windows must follow players (not built).
- **Rivers held:** `Field.hold_steady()` gives every face the Manning discharge of the baked surface slope (capped 3 m2/s and 6 m/s) and every headwater its spring; the hub also holds the sea (bed under 0) at level 0 and runs in channel mode (`set_channel_mask`: water only where the baked file has it, spill is dropped). Result on the starter window after 180 s: 2,694 of 2,732 baked wet cells still drawn (was 2,401, 88 percent; now 98.6), 0 newly flooded cells (was 322). Without channel mode the sim flooded the hillsides (5,000 to 8,000 cells), because the baked 13 cm film on steep channels is not a physical equilibrium.
- Honest limits: channel mode means rivers cannot widen or flood, rain falls only on channel cells (so runoff over hills is off in the game, on in the field tests), digs still do nothing. Springs derived from the baked slope are a reconstruction, not the real source data.

## Step 3 the game's shader on the new water: partly done, rated 3.5 of 5
`demo_water_field.gd` now draws the water with the game's own `water_material.gd` (per-vertex flow in COLOR, the game's ripples, depth-textured shore), traits in its uniforms. `art/valley_calm_vs_rough.png`: the SAME river at 4.7 m/s, left calm, right rough: **in the game the shader's `rough` is tied to the global flow rate; with the new water it is the trait `turbulence`, so fast-but-calm exists.** Not done: in the real game the flow is derived on the client from the received levels (WaterGrid `_velocities`), and the protocol carries levels only, so the sim's flow, depth and traits do not reach the shader there; that needs a protocol change (a flow channel per water chunk) which I have not made. Swamp and lava through the game shader look wrong (grey, brown, no glow: the shader has no emission uniform), so no kinds picture is posted this time.

## Step 4 if GDScript is not enough: options (cost, risk)
Measured: 92 ms of compute per simulated second for a 1 km window with 2,900 wet cells, on a 50 percent duty thread = 9 percent of a core. That is inside the budget for ONE window, so no native code is needed for the starter case. It is not enough for many windows (one per player) or a wide lake wake-up. Options when it is: (1) static lake levels, sim only for moving water: lakes already sleep after the rest snap, so this is mostly done; (2) skip stepping dry channel cells (a cell list instead of 16 x 16 blocks): about 2 to 3 times cheaper, 1 day, low risk; (3) a GDExtension in C++ for the flux and depth loops: about 20 to 50 times faster, 3 to 5 days, adds a build step and a platform binary to the repo (the main risk), keeps the same arrays; (4) compute shader on the client, server keeps the coarse state: biggest change, 5+ days, server and client could disagree. Recommendation: do (2) first if a second window is needed, (3) only if windows must cover whole tiles.
