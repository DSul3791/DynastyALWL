# Turning the camera between shots in our Godot client (Tyler, 25 Oct 2026; Dave: "look up the best way to turn the camera")
Status: from reading the code (src/debug/shot_runner.gd, scenes/terrain_client/terrain_client.gd on generator-v2 build 791). NOT run here (no display). David3 tests it on the box first; Mike second.

## Why the pictures do not turn (found in the code)
1. **Mouse look is live in shot mode.** terrain_client.gd line 2110 captures the mouse whenever the display is not headless; line 2799 rotates the body from every mouse motion event while captured: `body.rotate_y(-relative.x * 0.002)` and `pitch -= relative.y * 0.002`. Under Xvfb or on Mike's PC (Dave's pointer, or the first captured-mode pointer warp) any mouse movement of about 1,090 pixels is 124.8 degrees. The runner sets the pose once in `_next()` (line 1003: body.rotation, client.pitch, camera.rotation.x), but nothing stops later mouse events from rewriting it, so "asked 0.0, got 124.8" is mouse look, not a bad request.
2. **Pitch -90 reads as -85.9 because of the client clamp.** Line 2801 clamps pitch to plus or minus 1.5 rad = 85.94 degrees. That is expected, not a bug: the lowest look-down we can ask for is -85.9; ask for -85 and expect it exactly.

## The recipe (one change, three parts)
A. **Lock mouse look while shooting** (client, 3 lines, RUNTIME): add `var shot_lock := false` to terrain_client.gd; at line 2799 change the condition to `if event is InputEventMouseMotion and Input.mouse_mode == Input.MOUSE_MODE_CAPTURED and not shot_lock:`; shot_runner sets `client.shot_lock = true` when it starts (and `Input.mouse_mode = Input.MOUSE_MODE_VISIBLE` once, so a stray click cannot re-capture and the pointer does not hide the shot). Stopping the input at its source is more reliable than resetting the pose every frame.
B. **Set the pose just before each capture, then read it back.** `client.body.rotation.y = deg_to_rad(yaw)`; `client.pitch = clampf(deg_to_rad(pitch), -1.48, 1.48)`; `client.camera.rotation.x = client.pitch`. Wait 2 process frames, then compare the read-back (`rad_to_deg(client.body.rotation.y)` wrapped with angle_difference, and `client.pitch`) with the request: within 0.5 degrees. Print `pose: asked yaw=Y pitch=P got yaw=Y2 pitch=P2 ok|MISMATCH`. On mismatch retry up to 3 times, then shoot and mark the picture "pose mismatch" in the README (the batch fails the duplicate/pose check from STANDARD_SHOTS.md).
C0. **Third person and subject shots must NOT turn the body** (Dave watching Mike's run, 25 Oct 01:42): `_side_view()` in shot_runner.gd (line 847) places view_cam with the BODY's basis (`left = body.global_transform.basis * (-1,0,0)`), so any body turn turns the camera with the character and every picture is the same. Replace it with a world-space orbit: `angle = start_angle + k * PI/2` (k = 0, 1, 2); `view_cam.global_position = subject + Vector3(sin(angle) * dist, height, cos(angle) * dist)`; `view_cam.look_at(subject + Vector3(0, aim_height, 0), Vector3.UP)`. The character stays put, the camera goes round it, same distance and height. Read back the camera position and heading toward the subject (each view differs by 90 degrees around the subject, distance equal within 5 cm), not the body yaw. Subject = the character (third person), a tree, a shrub, the ground item group, or the placed piece. In shot mode the player camera is hidden/unused for these shots (client.third_person = true already does this).
C. **Turn left 90 degrees between the views of a PANORAMA spot (first person, look outward) only:** `client.body.rotation.y += PI / 2.0` (positive rotation about Y is counter-clockwise seen from above, which turns the camera to the left); then step B's read-back with the new target yaw; then capture.

## Options I rejected
- **Inject InputEventMouseMotion:** relative, depends on sensitivity, mouse mode and event order, drifts, and is the same path that is currently the problem.
- **Dedicated screenshot camera:** the runner already has view_cam for side views; but our pictures must show the real player camera (held items, arms, bobbing off), so the player camera stays the shot camera.
- **Resetting the pose every frame:** hides the cause, fights the game's own code and can tear a shot.
