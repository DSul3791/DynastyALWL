## The crash investigation (2026-10-21 evening to 2026-10-22)
Symptom: the game "closes by itself" while Dave plays from the editor (F6, Game tab embedded); once a black text box then flat gray embedded window then it closes after about a minute.
**Ruled out:** specific builds (happened on 236, 530, 546, 549), a fresh project folder (Dave deleted the project and branched from 530: same), GPU/driver (Tyler Report 27: client healthy at ~81 fps to the end), our quit paths (the only quit paths are the Quit button, test flags, and `_finish(1)` from `server_disconnected`).
**Finding:** it was NOT a client crash. The game quits with "server left" because the SERVER (a separate headless process the launcher starts with `--quit-when-empty`) stopped answering and ENet dropped the client. Dave's first telemetry showed the server main thread stalling 1 s, 5 s, 10 s, 43 s, 287 s while Dave held the dig click at one spot (same 0.9 m sphere dozens of times). Root cause: `ground_ops` stored radii as 32-bit floats, so 0.9 came back as 0.89999998 and `gap + radius <= radius_stored` never held; a repeated dig of the same spot was never coalesced. Each dig: new tile revision, `revisions.json` rewrite, `tile_changed` to every client (each client forgets prefetched blocks and re-asks), `dug` message, water wake. Also the client re-asked water for all held flora chunks about twice a second and the server answered each time (about 65 percent of server main thread). The headless repro (`--dig-spam=3` on the client, 150 s) gave a worst server gap of 64 s before and none over 2.4 s (after start-up) after build 592. Dave's description fits: the first voxel breaks, the next ones do not, then freeze.
**Not verified:** why builds as old as 236 also did it (digging with a held click existed since the admin X dig of 2026-10-19; unverified). Treat other freezes as open until Dave's logs say otherwise.
**Remaining server baseline cost:** `_poll_water` about 250 ms per frame on my 4-core Linux (Sonny's `water_live.gd` `take_levels` / water thread mutex), and a 1-3 s main-thread stall when a client joins ("items" step about 1.6 s in `items.tick` right after welcome: Radar's `server_items`). Both reported to the coordinator; not fixed.
**Telemetry files** (project folder `crash_reports/`, Dave commits and pushes them with GitHub Desktop):
- `telemetry_client.log` / `telemetry_server_<port>.log`: one line a second: `max gap N ms (slow steps ms: step N, ...)`, fps, ram, queues, packets/KB in the last second, ENet `rtt`, `loss` (scaled by 65536: 6553 = 10 percent; nonzero on localhost means the other side was not servicing the socket), `state` 5 = connected. `STALL:` lines are main-thread gaps over 0.5 s. `WATCHDOG:` lines (thread) name the step a frozen main thread is stuck in. Last lines: `EXIT:` with the reason (server_disconnected, quit code, window close request, exit_tree). The two files use the same clock format: line them up by time.
- `<date>_build<N>.txt` report: header says "quitting by itself: server left" (a lost connection) or "HUNG" (client main thread silent 15 s) or the flag-file case after a hard native death; contains breadcrumbs, last 40 errors, the server's last 60 telemetry lines, and the last 300 lines of Godot's own log (a native crash backtrace would be there).
- A hard native death leaves `user://running.flag`; the next start writes the report. `user://` = `%APPDATA%\Godot\app_userdata\Dynasty a life well lived\`.
- Editor-debugger theory (a script ERROR in an F6 run breaks the game in the debugger until someone presses Continue, and the server then drops it): plausible and still unproven; the report header says whether the run is from the editor with a debugger attached.
- The server also logs its own events: `user://`-free, in `crash_reports/telemetry_server_<port>.log` (port 24600 normally). If a stale old server still holds the port the new one writes `telemetry_server_failed.log`.

## Traps and gotchas
- `OS.create_process(OS.get_executable_path(), ...)` in the editor starts the EDITOR exe headless as the server; both processes write the same `user://logs/godot.log` (interleaved log).
- Godot `Logger` subclass receives script errors and warnings from all threads: handlers must be thread-safe (the crash reporter uses a mutex).
- `ENetPacketPeer.set_timeout` must be applied on each connection (server: in `_on_peer_connected`; client: on `connected_to_server`).
- `ENetConnection.pop_statistic` resets the counter, which is why telemetry shows a per-second rate.
- Starter cache must be rebuilt after any bake; tiles stamp mismatch means the client ignores it. Never commit `.tile` files from the cloud.
- `git pull --rebase` conflicts on `const BUILD` every time; resolve and keep going. Do not stash/commit other people's changes by mistake.
- `--quality=` takes 0..3 (the hole_stress script maps names).
- A multi-line statement cannot have `@warning_ignore` placed inside it; put it above the statement.
- Server `quit-when-empty`: with no player the headless server exits after 120 s; closing the game fully before F6 avoids a stale server on port 24600.
